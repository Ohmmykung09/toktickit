# Lab 2 Specification: TokTickIT Requester Ticketing MVP

## 1. Purpose and Scope

TokTickIT Lab 2 delivers a requester-facing IT support ticketing MVP. A user selects a temporary Development Requester identity, creates an IT support ticket, and manages only tickets and attachments owned by that requester.

The Development Requester selector is a testing context for Lab 2. It is not real authentication and must be replaceable by Lab 3 authentication.

### In Scope

- Development Requester selection and switching.
- Creating a ticket with category, related system, requested priority, summary, description, and optional attachments.
- My Tickets search, filters, sorting, pagination, and Ticket Detail.
- Uploading, downloading, and soft-removing permitted attachments.
- Zen Green responsive UI, automated tests, and documented API contracts.

### Out of Scope

- Login, passwords, sessions, tokens, and real role-based access control.
- IT staff workflows, assignment, comments, internal notes, and ticket resolution actions.
- Administrative maintenance screens.

## 2. Functional Requirements

| ID | Requirement |
| --- | --- |
| FR-01 | The system shall load active Development Requesters from PostgreSQL and allow one requester to be selected for Lab 2 testing. |
| FR-02 | The application shell shall display the selected requester and provide a Change Requester action. |
| FR-03 | The system shall load active Categories and Related Systems for the Create Ticket form. |
| FR-04 | The selected requester shall be able to create a ticket with Category, Related System, Ticket Summary, Requested Priority, Description, and optional attachments. |
| FR-05 | The backend shall create the official Ticket Number and return it after a successful ticket creation. |
| FR-06 | The selected requester shall be able to view a paginated list of only their own tickets. |
| FR-07 | My Tickets shall support search, category/status/priority filters, sorting, and pagination. |
| FR-08 | The selected requester shall be able to open read-only details for one ticket they own. |
| FR-09 | The selected requester shall be able to upload permitted attachments to a ticket they own. |
| FR-10 | The selected requester shall be able to view attachment metadata and download an active attachment from a ticket they own. |
| FR-11 | The selected requester shall be able to soft-remove an active attachment from a ticket they own. |
| FR-12 | The UI shall show loading, empty, no-result, success, validation-error, and request-failure states where applicable. |

## 3. Business Rules

| ID | Rule |
| --- | --- |
| BR-01 | The official Ticket Number is generated by the backend, is unique, and cannot be supplied or edited by the requester. The initial format is `TKT-YYYYMMDD-NNNN`. |
| BR-02 | Every newly created ticket starts with the status `New`. |
| BR-03 | Development Requester selection is for Lab 2 testing only and does not authenticate a real user. |
| BR-04 | Only active Development Requesters appear in the selector. A previously selected inactive requester cannot create or access requester ticket data. |
| BR-05 | Every Ticket belongs to exactly one Development Requester. Ticket list, detail, and attachment operations must verify ownership using the selected requester context. |
| BR-06 | Ticket Category and Related System must be active valid records supplied by the backend. |
| BR-07 | Ticket Summary is required, is trimmed, and must contain 5 to 120 characters. Description is required, is trimmed, and must contain 10 to 2,000 characters. |
| BR-08 | Requested Priority is required and must be one of `Low`, `Medium`, `High`, or `Critical`. |
| BR-09 | Permitted attachment extensions are JPG, JPEG, PNG, WEBP, and PDF. Each file is at most 5 MB. |
| BR-10 | A Ticket may have at most five active attachments. Soft-removed attachments do not count toward this limit. |
| BR-11 | Attachment removal is a soft removal. Removed attachments remain auditable but cannot be downloaded or previewed by requesters. |
| BR-12 | For each ticket-submit action, the frontend generates one UUID `Idempotency-Key` and disables duplicate submit actions while the request is in progress. The backend atomically records and checks the key for the selected requester: a retry with the same key and the same payload returns the original ticket without creating another ticket; reusing the key with a different payload returns `409 Conflict`. |
| BR-13 | When a create or upload request fails, the UI must keep entered ticket data and display a useful error message. A successful ticket is not rolled back when a later attachment upload fails. |

## 5. Data Design Decisions

- `DevelopmentRequester` owns many `Ticket` records. Lab 3 can later replace this relationship with an authenticated user identity without changing the ticket workflow.
- `Ticket` references one `Category` and one `RelatedSystem`; both lookup records have an active flag so historical tickets retain their references.
- `Attachment` belongs to one `Ticket` and has `removedAt` and `removedByRequesterId` for soft removal. Physical file deletion is not required in Lab 2.
- `Ticket` stores a unique idempotency key for the create request. This gives the backend a durable duplicate-submission check even when a client retries a request after a network failure.
- The ticket list will use indexes that support requester ownership and common list ordering, including requester plus creation time and Ticket Number uniqueness.

## 6. Acceptance Criteria by Feature

### AC-01 Development Requester Selection

- Active requesters load from the backend and can be selected.
- The selected requester is visible in the navigation and can be changed.
- Loading, empty, and backend failure states are understandable.

### AC-02 Create Ticket

- A valid selected requester can create a ticket and receive a unique Ticket Number.
- The created ticket has status `New` and is owned by that requester.
- Invalid fields, invalid lookup values, and duplicate submission are rejected safely.
- Retrying the same create request never creates a second ticket; reusing an idempotency key for different ticket data returns `409 Conflict`.

### AC-03 My Tickets and Ticket Detail

- A requester sees only their tickets.
- Search, filters, sorting, and pagination return predictable results and metadata.
- A requester cannot retrieve another requester's ticket by changing a URL or API parameter.

### AC-04 Attachments

- Permitted files within the file-count and size limits upload successfully.
- Invalid type, excessive size, excessive count, and non-owner operations fail safely.
- Soft-removed files are no longer downloadable or previewable.

### AC-05 User Experience

- Required UI screens use Zen Green styling and remain usable across desktop, tablet, and mobile widths.
- Relevant success, failure, loading, empty, and no-result states are present.

## 7. Definition of Done

A Lab 2 feature is done when its acceptance criteria are implemented, documented, and covered by appropriate automated tests. The feature must be developed on its feature branch, reviewed through a Pull Request into `lab2-staging`, and have any review comments resolved. The final release is complete only when all Lab 2 features, documentation, responsive evidence, test evidence, and release PR into `main` are complete.
